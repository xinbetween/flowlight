# Flowlight 0.18.6 enforcement and alert-review audit

Reviewed on 2026-11-17 for Flowlight 0.18.6 build 90.

## Scope

This correction addresses two observed advertising loads and the menu-bar alert-review dead end. It does not introduce response MIME filtering, URL-path filtering, HTTPS payload classification, cosmetic filtering, or broad YouTube/Facebook/Meta blocking.

## Runtime enforcement

The managed-pack diagnostics disclosure contains only configuration identity, capture-source name, generations, digests, apply state, and bounded status detail. It does not retain or expose browsing payloads or unrelated destinations. Exact enforcement requires the desired generation and digest to match both the extension acknowledgement and the proxy/inspection matcher; matching bytes acknowledged under a different transfer generation fail closed. Store filter loss clears the proxy matcher, changes the runtime state to watching-only, and refreshes diagnostics immediately.

An extension publication revision now advances when managed packs, ordinary rules, enforcing allowlists, or app-connection authority actually changes; unchanged durable-delivery health callbacks do not create synthetic revisions. A flow stores its terminal decision and revision, while an in-flight evaluation and a newer rearm request are tracked separately. Revision claims are serialized against publication mutation and reevaluation scanning, so a callback racing a policy update cannot be missed. Because Network Extension terminal `allow` verdicts end data callbacks, the provider retains each live socket and asynchronously coalesces publication notifications before using `update(_:using:for:)` to request one next byte in both directions from older terminal allows. That real callback can drop a newly forbidden multiplexed connection or return terminal allow again; unsettled flows and already-dropped flows remain untouched.

The split-SNI fixture uses stable AdSense entry 42470 and proves that the first TCP segment remains unsettled, the complete ClientHello yields `pagead2.googlesyndication.com`, the matcher identifies the intended pack/version/entry, and refusal-event construction preserves the exact host and stable provenance.

## Alert review and window presentation

Every menu-bar review action creates a new UUID-bearing navigation request before presenting the window. Alerts switches to the New-only database filter, clears stale rule filtering, loads under the current Focus scope, selects the requested row or newest row, and consumes only the matching request UUID. A stale asynchronous load cannot clear a later click.

The main-window presenter registers the actual `NSWindow`; it does not search titles. The main scene remains a `WindowGroup`, but restoration is disabled so macOS cannot revive overlapping legacy sessions whose stale sidebar state competes with app-wide deep links. One main scene is always constructed. On a background-only launch the presenter immediately orders that guaranteed window out and sets `isReleasedWhenClosed = false`, so both the launch-hidden state and a later user close retain the exact AppKit window. Presentation reuses that hidden, closed, visible, or minimized registration, deminiaturizes when necessary, makes it key, and only then activates the app; `openWindow(id:)` is a fallback only when no registration exists. Registration tolerates SwiftUI replacing a transient hidden window during construction, and duplicate registrations are retired only when a canonical presentation is chosen. Open Flowlight, Review Alerts, and the filter warning share this coordinator.
